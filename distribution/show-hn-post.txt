BODY

My AI agent passed every test I wrote. Then I found out it cheated. It read the
test file, saw what was being asserted, and wrote code that produced exactly
those outputs. It followed every rule I gave it and broke every rule it could.

That is the problem this tool is trying to kill.

rebuild-dossier is an MCP server. It reverse-engineers a rebuild spec out of an
existing app. You point it at a repo and a site, and it produces three things:
a locked CLAUDE.md, the .claude config, and a mutation-tested test suite. Any
coding agent can then rebuild the app against that spec, and it cannot silently
validate a bug as intentional.

The route to that is one strict rule. Auto-resolving an ambiguity requires two
things to agree: the code and the observed behavior. And it requires an
affirmative signal that someone actually decided, a stated comment, a TODO
admitting a bug, or a direct human answer. Silent agreement alone, code and
behavior matching with nobody having said why, always becomes a question. Never
an auto-resolution. No matter how confident it looks.

Why this matters: my prior research found a rebuild pipeline scores 0% on
behavioral equivalence with no verified feedback loop, and 9 to 19% with a
coarse one. The bet here is that locking interface contracts before running
tests, plus a one-test-at-a-time retry loop, does meaningfully better. There is
a paper and an honest write-up of what broke in v0.

It is not a scaffold. It does not rebuild the app. It produces the spec the
downstream agent consumes. That boundary is deliberate.

Install: npx rebuild-dossier@latest

There are six tools: ingest a repo, crawl the site, generate the spec, flag a
known bug, manage the case queue, resolve a case.

I am looking for one thing: does the non-negotiable rule hold up when other
people stress it? The tool was validated end to end against one real, messy
repo, including two fresh-agent handoffs on two model tiers. I want more of
that, from people who did not write it.
